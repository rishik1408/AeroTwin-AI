# AeroTwin AI — C-MAPSS Benchmark

This directory contains **`cmapss_benchmark.py`**, which validates that the
synthetic engine-fault data generated by AeroTwin AI is statistically
consistent with real-world turbofan degradation behaviour recorded in NASA's
**Commercial Modular Aero-Propulsion System Simulation (C-MAPSS)** dataset.

---

## 1 · Dataset Location

The NASA C-MAPSS data files are included in the repository under:

```
SIH 26/
└── data/
    └── cmapss/
        ├── train_FD001.txt
        ├── train_FD002.txt
        ├── train_FD003.txt
        └── train_FD004.txt
```

Each file contains multi-unit run-to-failure trajectories.  
`train_FD001.txt` (single operating condition, one fault mode) is the
recommended starting point for benchmarking.

> **Column layout of C-MAPSS files** (space-delimited, no header):  
> `unit_number | time_in_cycles | op_setting_1..3 | sensor_1..21`

---

## 2 · Generating the Synthetic Dataset

From the `simulation/` directory, run:

```bash
python generate_dataset.py --healthy 5 --faulty 3 --outdir dataset
```

This writes:
- **One CSV per mission** to `simulation/dataset/` — used by the ML training pipeline.
- **`simulation/dataset/all_missions.csv`** — a single combined file that
  concatenates every mission's rows under a shared header.  
  This is the file the benchmark script reads.

Each CSV contains two benchmark-compatibility columns at the front:

| Column | Description |
|---|---|
| `mission_id` | Unique string identifier for the simulated run (e.g. `healthy_0`, `fault_oil_pressure_drop_2`) |
| `tick` | Integer time-step counter within the mission starting at **0** |

---

## 3 · Running the Benchmark

```bash
cd simulation/benchmarks

python cmapss_benchmark.py \
  --cmapss      ../../data/cmapss/train_FD001.txt \
  --synthetic   ../dataset/all_missions.csv \
  --synthetic-col      oil_pressure_bar \
  --synthetic-id-col   mission_id \
  --synthetic-time-col tick
```

### Flag reference

| Flag | Default | Meaning |
|---|---|---|
| `--cmapss` | *(required)* | Path to the NASA C-MAPSS text file |
| `--synthetic` | *(required)* | Path to `all_missions.csv` |
| `--synthetic-col` | *(required)* | Telemetry column to compare (any numeric column) |
| `--synthetic-id-col` | *(required)* | Column grouping rows into per-mission runs (`mission_id`) |
| `--synthetic-time-col` | *(required)* | Integer tick index within each run (`tick`) |
| `--cmapss-sensor` | `5` | 0-based column index of the C-MAPSS sensor (default = sensor_1) |
| `--window` | `20` | Number of rows in the fault-active signature window |
| `--rul-cap` | `125` | Early-RUL cap for piecewise labelling |

Other useful `--synthetic-col` values: `cht_celsius`, `egt_celsius`,
`vibration`, `fuel_flow`.

## 4 · Understanding the Output

The benchmark prints two sections.

### 4a · KS-Test — degradation signature distributions

```
======================================================================
KS TEST RESULTS — degradation signature distributions
======================================================================
  Decline rate                    statistic=0.081  p=0.312  ✅ PASS (p > 0.05)
  Noise-to-signal ratio           statistic=0.064  p=0.589  ✅ PASS (p > 0.05)

  ✅ OVERALL PASS
```

The script computes a **two-sample Kolmogorov–Smirnov (KS) test** on two
signatures extracted from the **fault-active window** of each mission:

| Signature | What it captures |
|---|---|
| **Decline rate** | Per-tick linear slope of the sensor column during the fault, from fault onset to the last fault-labelled row |
| **Noise-to-signal ratio** | High-frequency residual variance relative to the trend — captures sensor noise characteristics |

> **Why fault-active window, not last 20 rows?**  
> Every mission ends with a descent/shutdown phase where throttle drops to
> zero. That creates a spurious "decline" at the tail of even healthy
> missions. By limiting the window to rows where `label_fault_type` is
> non-healthy, we compare only genuine degradation behaviour.

#### Interpreting p-values

| p-value | Interpretation |
|---|---|
| **p > 0.05** ✅ | **Pass.** The two distributions are not statistically distinguishable. Our synthetic degradation curves are consistent with real C-MAPSS behaviour. |
| **p ≤ 0.05** ❌ | **Fail.** The distributions differ significantly. Tune onset timing, severity range, or noise parameters in `faults.py`. |

> **Rule of thumb:** aim for p > 0.05 on *both* signatures before using
> the synthetic data to train a production-grade anomaly detector.

The KS test is non-parametric — it makes no assumption about the shape of
the degradation distribution, which is appropriate because real engine
wear curves are rarely Gaussian.

### 4b · RUL-vs-parameter correlation

```
======================================================================
RUL-VS-PARAMETER CORRELATION (Pearson r, whole-run)
======================================================================
  C-MAPSS                         n= 100  mean r=-0.612  std=0.143
  Synthetic                       n=  24  mean r=-0.589  std=0.178

  |Δ mean r| = 0.023  →  ✅ consistent
```

For each mission the script builds a piecewise-linear RUL curve (flat at
the early-life cap, then declining to 0 at the last tick) and computes
the Pearson correlation between that curve and the chosen sensor column.

| Δ mean r | Interpretation |
|---|---|
| **< 0.15** ✅ | Both datasets show a similarly-shaped RUL-vs-parameter relationship. The synthetic degradation trajectory is validated. |
| **≥ 0.15** ⚠️ | The RUL shape differs between datasets. Consider adjusting fault duration or severity progression in `faults.py`. |

## 5 · Extending the Benchmark

- **Different fault modes:** filter `all_missions.csv` to rows where
  `label_fault_type == <mode>` and pass that subset to `--synthetic`.
- **Different sensors:** change `--synthetic-col` to any numeric column
  (e.g. `egt_celsius` maps naturally to C-MAPSS temperature sensors).
- **FD002–FD004:** repeat with the multi-condition files to stress-test
  robustness across operating regimes.
